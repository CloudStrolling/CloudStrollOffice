## 1. 业务目标
本版本为云漫智企（CloudStrollOffice）的初始化基线版本，目标是为企业提供一个**统一认证授权与企业办公的微服务化平台底座**，达成以下业务目标：

- **G1 统一认证入口**：为企业员工、管理员及第三方系统提供统一的身份认证能力，支持 6 种客户端类型（Windows/Ubuntu/H5/Android/iOS/微信小程序）通过同一套账号体系混合登录，实现"一次认证、多端通行"。
- **G2 多模式登录/注册**：支持用户名密码、手机验证码、手机+密码、OAuth 第三方共 4 种登录模式，以及用户名密码、手机验证码、OAuth 共 5 种注册策略（含两步注册），降低用户进入门槛，覆盖不同使用习惯的终端用户。
- **G3 多租户权限隔离**：基于 RBAC（用户-角色-权限）模型实现多租户数据隔离，支持租户内用户名唯一、租户间数据不可见，满足多企业共用一套系统的 SaaS 场景。
- **G4 安全会话与访问控制**：基于 JWT RS256 双 Token（Access Token 2 小时 + Refresh Token 7 天 + 轮换机制）与 Redis 会话管理，实现登录态实时可控（登出、强制踢人、密码重置后全端下线），网关统一 9 步认证拦截，保障 API 访问安全。
- **G5 账号安全自助能力**：提供密码修改、密码找回（短信/邮箱验证码）、手机号变更、账号信息补全等自助服务，减少管理员干预，提升账号安全性与用户体验。
- **G6 业务骨架就绪**：认证服务完整可用（9 张数据表、12 个认证端点、用户/角色/权限管理 API），企业服务与系统服务骨架搭建完成（健康检查），为后续企业信息管理、人事管理、工作流审批、薪酬管理等业务版本迭代提供可扩展底座。
- **G7 客户端多端可用**：Flutter 客户端支持 Web 与 Windows 双平台，提供登录、注册、忘记密码等核心认证页面，可直接对接后端认证服务。

**量化指标**：本版本实现认证服务 9 张数据表、12 个认证类 API 端点、8 个用户/角色/权限管理端点、4 种登录策略与 5 种注册策略、29 个统一错误码、全量单元测试通过（认证服务 200+ 用例），并可经 Docker Compose 一键编排 8 个容器完成部署。

## 3. 业务场景
### 3.1 场景一：新用户注册并首次登录
- **触发条件**：企业员工或外部用户首次使用系统，尚无账号。
- **参与角色**：终端用户（访客）。
- **操作流程**：
  1. 用户打开客户端（Web/Windows/H5 等），进入注册页面；
  2. 选择注册模式：用户名密码注册（填写登录名、密码、姓名、租户编码）或手机验证码注册（填写手机号，点击发送验证码并输入收到的短信验证码）；OAuth 用户可经第三方授权直接注册；
  3. 系统校验参数合法性（密码长度 8-64、验证码有效、登录名/手机号租户内唯一）后创建账号并分配默认角色；
  4. 系统返回用户信息与双 Token，用户自动登录进入首页；账号信息不完整的用户（如 OAuth 注册）进入"完善账号信息"环节补全登录名、密码、手机号。

### 3.2 场景二：多模式登录与多端会话
- **触发条件**：用户已有账号，在任意客户端登录系统。
- **参与角色**：终端用户。
- **操作流程**：
  1. 用户在登录页选择登录方式：用户名+密码、手机+验证码、手机+密码、OAuth 第三方登录；
  2. 用户输入租户编码、凭据并选择客户端类型（Windows/Ubuntu/H5/Android/iOS/WeChatMini）；
  3. 系统校验租户状态、账号状态、密码/验证码，执行同端互斥（同一客户端类型只保留最新会话）、多端共存（不同端可同时在线）策略；
  4. 登录成功签发 JWT RS256 双 Token（Access Token 2 小时 + Refresh Token 7 天），返回给客户端，登录日志记录审计；
  5. 客户端持 Access Token 访问业务接口；Access Token 过期时携带 Refresh Token 自动刷新换取新 Token 对（旧 Refresh Token 进入黑名单）。

### 3.3 场景三：会话安全控制（登出/强制踢人/全端下线）
- **触发条件**：用户主动登出、管理员强制下线某用户，或账号发生安全事件（密码修改/找回）。
- **参与角色**：终端用户、系统管理员。
- **操作流程**：
  1. 用户主动登出：客户端携带 Access Token 调用登出接口，Token 加入 Redis 黑名单，登录态会话清除（幂等，重复登出不报错）；
  2. 管理员强制踢人：管理员在用户管理中对指定用户执行强制下线，可指定客户端类型（踢指定端）或不指定（踢所有端），被踢用户的下一次请求立即失效；
  3. 密码修改/找回重置成功后，系统自动清除该用户全部客户端类型的登录态会话，用户需重新登录。

### 3.4 场景四：密码管理与手机号变更
- **触发条件**：用户忘记密码、需要修改密码，或更换手机号。
- **参与角色**：终端用户。
- **操作流程**：
  1. 修改密码：登录用户提交旧密码与新密码，系统校验旧密码正确性及新密码策略（长度 8-64），成功后清除所有登录态；
  2. 忘记密码：用户点击"忘记密码"，输入手机号或邮箱，系统发送重置验证码（60 秒发送频率限制、5 分钟有效），用户输入验证码与新密码完成重置，成功后清除所有登录态；
  3. 手机号变更：原手机号可用时通过原手机短信验证码变更；原手机号停用时通过邮箱验证码变更；变更成功后新手机号生效。

### 3.5 场景五：RBAC 权限管理与租户隔离
- **触发条件**：管理员需要维护租户内的用户、角色、权限体系。
- **参与角色**：系统管理员、租户管理员。
- **操作流程**：
  1. 管理员查看用户分页列表、用户详情，创建/更新/删除用户，调整用户状态（封禁/解封，封禁后登录与访问立即失效）；
  2. 管理员创建角色、维护权限树（树形结构），并为角色分配权限（角色-权限多对多）；
  3. 管理员为用户分配角色（用户-角色多对多），用户即获得角色对应的权限集合；
  4. 所有数据操作均按租户隔离：用户名在租户内唯一，租户间数据不可见。

### 3.6 场景六：网关统一认证与健康检查
- **触发条件**：任意客户端请求受保护的业务 API，或运维人员验证系统可用性。
- **参与角色**：终端用户、第三方系统、运维人员。
- **操作流程**：
  1. 客户端请求经网关转发；AuthFilter 执行 9 步校验：白名单放行（登录/注册/刷新/验证码/密码找回/健康检查等）→ Bearer 格式校验 → RS256 公钥验签 → tokenType 校验 → Redis 黑名单校验 → 登录态校验 → 账号状态校验 → 租户状态校验 → 用户信息 Header 透传（X-User-Id 等）至下游服务；
  2. 校验失败返回统一 401/403 错误响应，校验通过后请求路由至目标微服务；
  3. 运维人员通过 `/api/v1/{auth|biz|system}/health` 健康检查端点确认各服务状态，通过 Swagger UI（OpenAPI 3）在线调试接口。

## 6. 约束条件
- **技术约束**：后端基于 Java 21 + Spring Boot 3.2.5 + Spring Cloud 2023.0.1；ORM 使用 MyBatis-Plus 3.5.6；JWT 使用 JJWT 0.12.6；数据库使用 MariaDB 10.6 (LTS)；缓存使用 Redis 7.2.x；注册/配置中心使用 Nacos 2.3.x；客户端使用 Flutter（Dart 3，SDK ^3.12.2），依赖 dio 5.4、provider 6.1、go_router 14.2、flutter_secure_storage_x 13.1。
- **架构约束**：Maven 多模块架构，公共代码统一放 cloudoffice-common，auth/biz/system 模块只依赖 common，禁止模块间互相依赖与循环依赖；API 路径统一规范 `/api/v1/{module}/{resource}`；包根为 `org.cloudstrolling.cloudoffice.{模块}`。
- **数据约束**：本版本认证库 `cloudstroll_office_auth` 共 9 张表（用户/租户/角色/权限/用户角色/角色权限/登录日志/OAuth 账号/验证码记录）；biz/system 库仅建库预留；初始数据含默认租户 DEFAULT、超级管理员角色 SUPER_ADMIN、管理员账号 admin（admin123）及基础权限数据。
- **业务约束**：用户名/手机号在租户内唯一；同一客户端类型仅允许一个在线会话（同端互斥），不同客户端类型可同时在线（多端共存）。
- **合规与开源约束**：项目遵循 Apache License 2.0 开源协议；代码文件保留 SPDX-License-Identifier 与版权声明。
- **时间约束**：本版本为初始化基线版本（v0.0.1 反推存量代码 v0.1.6 能力），后续按版本规划迭代企业信息、人事、工作流、薪酬等业务能力。

## 7. 假设与依赖
- **假设**：
  - 假设企业通过 SaaS 多租户方式使用系统，每个企业对应一个租户数据空间；
  - 假设生产环境短信/邮件通道由真实服务商提供，开发与测试环境可使用模拟验证码模式（VERIFICATION_CODE_MOCK=true，直接返回固定验证码）；
  - 假设用户通过公司内部网络或公网 HTTPS 访问系统，网络连通性由基础设施保障；
  - 假设管理员账号（admin/admin123）由部署方在首次部署后立即修改密码；

## 6. 约束条件

- **技术约束**：脚本体系为 Windows PowerShell（.ps1）与 Linux Bash（.sh）双平台，脚本需在两种 shell 语法下分别实现且行为对齐；后端服务为 Java 21 + Spring Boot 3.2.5 + Spring Cloud 2023.0.1，启动命令为 `java -Xms256m -Xmx512m -jar <jar>`；部署资产集中化策略下 jar 与 env.json 均位于 `deploy` 目录。
- **基础设施约束**：MariaDB 10.6（3306）、Redis 7.2（6379）、Nacos 2.3（8848）为外部依赖，脚本只能检测与驱动其启动，不负责安装；Nacos 启动依赖 `NACOS_HOME` 配置及其 startup 脚本。
- **契约约束**：RSA 密钥格式契约（DER 编码单行 Base64，公钥 X.509 / 私钥 PKCS#8）为 v0.2.6 确立并验证的契约（ADR-015），脚本重构不得破坏该契约；.sh 与 .ps1 行为必须一致。
- **范围约束**：本版本聚焦 `deploy/scripts` 脚本重构与 `.gitignore` 治理，不修改后端业务代码与接口契约；`deploy` 目录内最终产物（jar、客户端产物）与 `scripts/sql`、`scripts/docker`、`scripts/API-TEST` 等非脚本资产不在重构范围（如发现问题列入待办）。
- **合规约束**：遵循 Apache License 2.0；脚本文件保留 SPDX-License-Identifier 与版权声明；严禁提交密钥、口令等敏感信息。

| NFR-001 | 性能 | 通用配置查询接口响应时间 | 单次查询 ≤ 200ms（本地缓存命中时 ≤ 50ms） |

| NFR-004 | 可扩展性 | 通用配置管理接口设计支持后续增删改接口与管理界面的平滑扩展 | 接口层预留扩展点，数据层支持读写扩展 |
| NFR-005 | 部署一致性 | deploy-start-all/deploy-stop-all 双平台（.ps1/.sh）行为一致，输出分级与退出码约定统一 | 与 v0.2.7 脚本体系约定一致 |
| NFR-006 | 安全性 | 通用配置查询接口需经网关 AuthFilter 认证（非白名单端点），配置中敏感信息（如密码、密钥）不在查询接口返回 | 敏感配置项脱敏或排除 |

## 6. 约束条件
- **技术约束**：cloudoffice-common 服务化改造须基于现有技术栈（Java 21 + Spring Boot 3.2.5 + Spring Cloud 2023.0.1 + Spring Cloud Alibaba 2023.0.1.0），须引入 spring-cloud-starter-bootstrap 依赖保证 Nacos 配置引导链路正常；不得引入与现有技术栈重复的第三方框架。
- **架构约束**：common 作为公共模块被 gateway/auth/biz/system 依赖，服务化改造后不得破坏现有模块依赖关系（下游服务仍可依赖 common 的公共类与接口）；common 服务自身注册到 Nacos，网关统一路由 /api/v1/common/**。
- **部署约束**：cloudoffice-common 的 jar 包须输出到 deploy 目录；deploy-start-all 中 common 须在服务清单第一位执行（所有后端服务中最先启动）；deploy-stop-all 中 common 须在所有后端服务中最后停止。
- **配置范围约束**：通用配置管理仅管理运行时配置，启动环境变量（NACOS_ADDR、DB_PASSWORD、RSA_PUBLIC_KEY、RSA_PRIVATE_KEY、NACOS_HOME 等）不纳入通用配置管理范围，仍由 env.json 环境变量注入。
- **版本范围约束**：本版本仅交付配置查询接口，不包含配置增删改接口与后端管理界面。
- **脚本体系约束**：部署脚本更新须遵循 v0.2.7 脚本体系约定（load-env 统一加载 env.json、输出分级通过/警告/失败、退出码失败非零、.ps1 与 .sh 双平台行为一致）。

## 7. 假设与依赖
- **假设**：cloudoffice-common 服务化后分配独立端口（具体端口由详细设计确定，建议在 9300 或其他未占用端口）。
- **假设**：通用配置管理的配置数据存储方案（数据库表或 Nacos 配置中心或 Redis 缓存）由详细设计阶段确定，本 URS 不限定存储方案。
- **假设**：通用配置管理接口经网关路由 /api/v1/common/** 转发，需在网关路由配置中新增 common 路由规则。
- **依赖**：cloudoffice-common 服务化依赖 Nacos 注册中心与配置中心正常运行。
- **依赖**：通用配置管理接口依赖网关 AuthFilter 认证体系（非白名单端点需携带合法 Bearer Token）。
- **依赖**：现有 gateway/auth/biz/system 服务对 common 公共模块的 Maven 依赖关系不受服务化改造影响。
