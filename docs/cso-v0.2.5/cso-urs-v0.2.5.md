# 用户需求说明书（URS）
**项目名称**：云漫智企（CloudStrollOffice）
**版本号**：v0.2.5
**日期**：2026-08-09
**编写人**：BA

## 1. 业务目标
本版本旨在统一项目部署产物与部署脚本的管理，实现"构建产物集中化、部署配置集中化"的目标：
- 建立统一的 `deploy` 目录，作为项目所有最终构建产物（后端微服务 jar 包、客户端安装文件/exe 等）的唯一落盘位置，改变当前产物分散在各自模块输出目录的局面，使发布、打包、分发人员只需在一个目录即可获取全部可交付产物。
- 将环境配置（env.json、env.example.json）与部署运维脚本（scripts 下的 .sh/.ps1）统一收拢至 `deploy` 目录，使项目根目录结构更清晰：源代码与构建配置保留在根目录及模块目录，所有"运行/部署相关"资产集中在 `deploy` 下。
- 构建过程中产生的中间产物（如编译临时文件、测试产物、过程文件等）不得进入 `deploy` 目录，确保该目录只包含可直接交付/运行的最终产物。

## 2. 用户角色
| 角色名称 | 角色说明 | 使用场景 |
| --- | --- | --- |
| 后端开发工程师 | 负责 Maven 多模块（auth-service、biz-service、system-service、gateway）的编译与打包 | 执行 `mvn package` 后，在 deploy 目录获取各服务的最终 jar 包，而不是在各自 target 目录中查找 |
| 客户端开发工程师 | 负责 Flutter 客户端（Web/Windows）的构建与打包 | 构建完成后，在 deploy 目录获取安装文件/exe 等最终产物 |
| 运维/部署工程师 | 负责环境配置、数据库初始化、密钥生成、服务启停 | 在 deploy 目录下统一使用 env.json/env.example.json 与 scripts 子目录中的 .sh/.ps1 脚本完成部署与运维操作 |
| 发布/交付人员 | 负责将版本产物整理并交付 | 直接从 deploy 目录收集全部最终产物进行打包交付 |

## 3. 业务场景
### 3.1 版本构建与产物集中收集
- 触发条件：开发完成一个版本，需要构建全量可交付产物。
- 参与角色：后端开发工程师、客户端开发工程师、发布/交付人员。
- 操作流程：
  1. 后端开发工程师对 Maven 各模块执行打包；构建配置修改后，各服务生成的最终 jar 包统一输出到 `deploy` 目录。
  2. 客户端开发工程师构建 Flutter 客户端，生成的安装文件/exe 等最终产物输出到 `deploy` 目录。
  3. 发布/交付人员打开 `deploy` 目录即可看到全部最终产物，直接整理交付；构建中间产物不会出现在该目录中。

### 3.2 环境配置统一管理
- 触发条件：初始化环境或修改运行环境参数。
- 参与角色：运维/部署工程师。
- 操作流程：
  1. 运维/部署工程师在 `deploy` 目录下找到 `env.example.json` 模板与 `env.json` 实际配置。
  2. 按模板复制生成/修改 `env.json` 中的数据库、Redis、Nacos 等连接参数。
  3. 相关部署脚本从 `deploy` 目录读取 `env.json` 完成环境初始化与配置校验。

### 3.3 部署运维脚本统一使用
- 触发条件：执行数据库初始化、RSA 密钥生成、服务启动等运维操作。
- 参与角色：运维/部署工程师。
- 操作流程：
  1. 运维/部署工程师进入 `deploy/scripts` 子目录，找到对应的 .sh（Linux/macOS）或 .ps1（Windows）脚本。
  2. 按目标平台选择对应脚本执行部署运维操作，无需再分散到项目根目录的 scripts 目录查找。

## 4. 功能需求（高层）
| 需求编号 | 需求名称 | 需求描述 | 优先级 |
| --- | --- | --- | --- |
| FR-001 | 新建 deploy 目录 | 在项目根目录新建 `deploy` 目录，作为最终构建产物、环境配置与部署脚本的统一存放位置 | 高 |
| FR-002 | 后端 jar 产物输出到 deploy | 修改构建配置，使 Maven 多模块（auth-service、biz-service、system-service、gateway）打包生成的最终 jar 包输出到 `deploy` 目录 | 高 |
| FR-003 | 客户端安装产物输出到 deploy | 修改客户端构建配置，使 Flutter 客户端构建生成的安装文件/exe 等最终产物输出到 `deploy` 目录 | 高 |
| FR-004 | 中间产物不入 deploy | 构建阶段的中间产物（编译临时文件、测试产物、过程文件等）不得复制/输出到 `deploy` 目录，仅最终产物可进入 | 高 |
| FR-005 | env.json 与 env.example.json 迁移 | 将项目根目录下的 `env.json` 与 `env.example.json` 迁移到 `deploy` 目录，并确保相关部署脚本仍能正确引用 | 高 |
| FR-006 | deploy/scripts 子目录建立 | 在 `deploy` 目录下新建 `scripts` 子目录 | 高 |
| FR-007 | scripts 下 sh/ps1 脚本迁移 | 将项目根目录 `scripts` 下的全部 `.sh` 与 `.ps1` 文件迁移至 `deploy/scripts` 子目录，并确保脚本内引用的路径仍能正确工作 | 高 |

## 5. 非功能需求（高层）
| 编号 | 类别 | 需求描述 | 指标 |
| --- | --- | --- | --- |
| NFR-001 | 目录整洁性 | `deploy` 目录内仅包含最终产物、环境配置与部署脚本，无中间产物混入 | 构建完成后，deploy 目录中不出现 target 类中间目录/临时文件 |
| NFR-002 | 可维护性 | 产物与部署资产集中管理，路径引用清晰、可追踪 | 部署脚本中环境配置路径与 deploy 目录结构一致，无残留指向旧路径的引用 |
| NFR-003 | 兼容性 | 迁移后原有部署运维功能不受影响 | 迁移后 .sh/.ps1 脚本可正常执行，env.json 可被正确加载 |
| NFR-004 | 构建成功率 | 修改构建配置后，各模块构建仍可成功完成 | Maven 各模块 package 成功、Flutter 构建成功，产物正确落位 |

## 6. 约束条件
- 项目为 Maven 多模块微服务架构（Java 21 / Spring Boot 3.2.5）与 Flutter 客户端（Dart 3）双技术栈，构建配置需分别适配 Maven 与 Flutter 的产物输出机制。
- `scripts` 目录下除 .sh/.ps1 外的其他内容（如 sql、docker、API-TEST、文档等）不在本次迁移范围内，不得随迁移移动。
- 迁移必须保证现有部署脚本、环境配置引用关系完整可用，不能因路径变化导致部署流程失效。

## 7. 假设与依赖
- 假设：`deploy` 目录作为新资产根目录后，项目文档（readme、部署指南等）将随之更新路径说明（由后续版本/任务处理）。
- 依赖：Maven 各模块构建配置（pom.xml 或插件配置）、Flutter 构建配置（如 pubspec/CMake 等）支持自定义产物输出目录。
- 依赖：现有 `scripts` 目录下的 .sh/.ps1 脚本在迁移后需要同步调整内部对 `env.json`、`keys` 等资源的相对/绝对路径引用。
