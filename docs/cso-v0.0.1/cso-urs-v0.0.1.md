# 用户需求说明书（URS）
**项目名称**：云漫智企（CloudStrollOffice）
**版本号**：v0.0.1
**日期**：2026-08-05
**编写人**：BA

## 1. 业务目标
云漫智企（CloudStrollOffice）定位为企业级微服务办公套件，为中小型企业提供企业信息管理、人事管理、工作流审批、薪酬管理、统一认证授权等一站式综合服务能力。本版本（业务版本 v0.1.6，初始化归档版本 v0.0.1）聚焦建设**统一认证与权限管理基础平台**，为后续企业业务模块（biz-service）与系统管理模块（system-service）提供可复用的认证授权底座。具体业务目标如下：

- **统一认证入口**：建设基于 API 网关 + 认证服务的统一认证体系，支持 PC 端、H5、Android、iOS、微信小程序等 6 种客户端类型经统一入口登录，实现一次登录、全端通行。
- **多模式登录注册**：支持 4 种登录模式（用户名密码、手机验证码、手机+密码、OAuth 第三方）与 5 种注册模式（用户名密码、手机验证码、OAuth、手机号设用户名、OAuth 补全信息），覆盖员工 PC 办公、移动端快捷登录、第三方账号接入等常见场景，注册流程支持两步注册（先注册后补全信息），降低首次使用门槛。
- **统一权限管理**：建立 RBAC 多租户权限模型（用户-角色-权限三层关联 + 租户隔离），管理员可通过可视化 API 完成用户、角色、权限的维护与分配，用户名在租户内唯一、租户间数据不可见。
- **安全可信的账号生命周期管理**：支持密码修改与密码找回（验证码重置）、手机号变更（原手机可用走短信验证、原手机停用走邮箱验证）、验证码全生命周期管理（生成/发送/校验/频率控制）、登录日志审计，保障账号安全与事后追溯。
- **会话安全与实时管控**：采用 JWT RS256 双 Token（Access Token 2h + Refresh Token 7d，轮换机制）+ Redis 登录态会话管理，支持主动登出、管理员强制踢人实时生效、Token 黑名单防重放。
- **多租户隔离**：租户数据空间相互独立，支持多企业共用一套系统，为 SaaS 化运营奠定基础。
- **可量化验收目标**：本版本认证相关核心链路（登录、注册、Token、会话、密码、验证码）单元测试 206+ 个全部通过；9 张业务表完成初始化；4 个微服务 + 网关可经 Docker Compose 一键编排部署（8 个容器）。

## 2. 用户角色
| 角色名称 | 角色说明 | 使用场景 |
| --- | --- | --- |
| 系统管理员（SUPER_ADMIN） | 系统级超级管理员，拥有全部权限，可管理租户、用户、角色、权限及强制踢人 | 初始化系统、创建租户与管理员、维护权限树、全局安全管控 |
| 企业管理员 | 企业（租户）内的管理员，管理本租户员工账号、分配角色权限 | 员工入离职账号开通/停用、角色与权限分配、强制下线异常账号 |
| 普通员工 | 企业内一般员工，使用本系统办公，可自助管理自身账号 | 登录/注册、修改密码、找回密码、更换手机号、完善账号信息、日常办公 |
| 访客/未注册用户 | 尚未注册或尚未补全账号信息的用户 | 注册账号（多种模式）、两步注册第二步补全账号信息 |
| OAuth 第三方用户 | 通过微信、Gitee 等第三方平台授权登录的用户 | 第三方授权登录、第三方账号关联、补全本地账号信息 |
| 系统运维人员 | 负责系统部署、监控与维护的人员 | 服务健康检查、查看登录日志、监控认证服务运行状态 |

## 3. 业务场景
### 3.1 员工多模式登录
- **触发条件**：员工需要进入办公系统进行日常办公。
- **参与角色**：普通员工、企业管理员、系统管理员。
- **操作流程**：员工在客户端（PC/H5/App/小程序等）选择登录模式（用户名密码、手机验证码、手机+密码或 OAuth 授权）→ 输入凭证并选择租户与客户端类型 → 认证服务执行 13 步完整登录流程（账号校验、密码/验证码/OAuth 校验、租户状态校验、会话管理）→ 签发双 Token（Access Token 2h + Refresh Token 7d）→ 网关 AuthFilter 对后续请求执行 9 步全局认证校验（白名单放行、RS256 公钥验签、Token 类型校验、黑名单检查、登录态、账号状态、租户状态、Header 透传）→ 登录成功进入系统。同一客户端类型同端互斥、不同客户端类型多端共存。
- **业务规则**：同一端重复登录会顶掉旧会话；登录失败（密码错误、账号封禁、租户停用）需记录登录日志并给出明确错误提示。

### 3.2 新用户注册与账号补全
- **触发条件**：新员工或外部用户需要开通账号进入系统。
- **参与角色**：访客/未注册用户、系统管理员。
- **操作流程**：用户选择注册模式（用户名密码、手机验证码、OAuth 等）→ 填写注册信息并通过验证码/第三方授权校验 → 系统创建账号并分配默认角色 → 返回注册结果（用户信息 + Token 对）。若为两步注册（如手机号设用户名、OAuth 补全信息），用户首次登录后进入账号补全环节：设置登录名、密码、手机号（PUT /account/settlement）→ 补全成功后账号状态转为已完善。
- **业务规则**：用户名在租户内唯一；验证码注册需校验验证码有效性；注册成功直接返回 Token 对，登录后即可使用系统。

### 3.3 企业组织与权限管理
- **触发条件**：企业管理员需要维护本企业组织与人员权限。
- **参与角色**：企业管理员、系统管理员。
- **操作流程**：管理员通过用户管理接口分页查询员工列表、查看员工详情、更新员工信息、封禁/解封账号（状态管理）、为员工分配角色；通过角色管理接口创建/修改/删除角色并为角色分配权限；通过权限管理接口维护树形权限结构。
- **业务规则**：用户-角色、角色-权限均为多对多关联；账号封禁后所有登录态实时失效（网关校验账号状态拦截）；权限以树形结构组织便于分级管理。

### 3.4 账号安全与自助管理
- **触发条件**：员工遗忘密码、怀疑账号被盗、更换手机号等。
- **参与角色**：普通员工。
- **操作流程**：
  - 修改密码：登录状态下提供旧密码校验，新密码需满足 8-64 位策略 → 修改成功后自动清除该用户所有登录态会话，需重新登录。
  - 密码找回：未登录状态通过手机短信或邮箱发送重置验证码（60 秒频率限制、5 分钟过期）→ 校验验证码后重置密码 → 清除所有登录态。
  - 更换手机号：原手机可用时通过原手机短信验证码验证变更；原手机停用时通过已绑定邮箱验证码验证变更。
- **业务规则**：密码修改/重置成功后强制清除全部登录态；验证码发送受频率控制（默认 60 秒间隔）、过期时间（默认 5 分钟）、长度（默认 6 位）约束；敏感操作（登录失败、Token 失效、改密、验证码发送）必须留痕日志。

### 3.5 安全管控与审计
- **触发条件**：管理员发现异常账号或需要审计登录行为。
- **参与角色**：系统管理员、企业管理员、运维人员。
- **操作流程**：管理员通过强制踢人接口指定用户 ID（可选指定客户端类型）将用户强制下线，实时清除其登录态；运维人员通过登录日志表（t_auth_login_log）追溯登录 IP、客户端类型、登录结果与失败原因；通过健康检查端点（/api/v1/{module}/health）确认各服务运行状态。
- **业务规则**：踢人后目标用户的 Access Token 立即失效（黑名单实时生效）；Token 过期/被踢后的请求由网关返回标准 401 JSON 响应。

### 3.6 系统部署与运维
- **触发条件**：系统首次上线或扩容部署。
- **参与角色**：系统运维人员。
- **操作流程**：按环境要求准备 JDK 21、Maven 3.9+、MariaDB 10.6、Redis 7.2.x、Nacos 2.3.x → 执行 SQL 初始化脚本创建数据库与 9 张业务表及初始数据（默认租户 DEFAULT、超级管理员角色、admin 用户）→ 配置 RSA 密钥与环境变量 → 编译打包 → 按顺序启动 Nacos、Gateway、Auth、Biz、System 服务（或使用 Docker Compose 一键编排 8 个容器）→ 通过健康检查端点验证部署成功。
- **业务规则**：RSA 私钥/公钥通过环境变量注入，禁止提交密钥文件；验证码模拟模式开关（VERIFICATION_CODE_MOCK）用于开发环境，生产环境必须关闭。

## 6. 约束条件
- **技术约束**：后端采用 Java 21（LTS）+ Spring Boot 3.2.5 + Spring Cloud 2023.0.1 + Spring Cloud Alibaba（Nacos 2.3.0）+ MyBatis-Plus 3.5.6 + JJWT 0.12.6；前端采用 Dart 3（Flutter）；数据库采用 MariaDB 10.6（LTS）与 Redis 7.2.x；构建工具 Maven 3.9+。
- **架构约束**：采用 Maven 多模块微服务架构（common/gateway/auth-service/biz-service/system-service + flutter-app），服务间通过 Nacos 服务发现通信，禁止循环依赖；接口路径遵循 /api/v1/{module}/{resource} 规范。
- **安全约束**：密码长度 8-64 位；验证码 6 位数字、默认 5 分钟过期、60 秒发送间隔；RSA 2048 位密钥对用于 JWT RS256 签名；敏感信息（私钥、数据库密码）禁止提交至版本库。
- **法规与合规约束**：用户账号与登录日志涉及个人信息与安全审计数据，需遵循个人信息保护相关法规，敏感信息加密存储、日志留痕不泄露。
- **版本约束**：本版本为初始化归档版本 v0.0.1，对应实际业务版本 v0.1.6；biz-service 与 system-service 仅提供骨架与健康检查，企业信息管理、人事管理、工作流审批、薪酬管理等业务功能在后续版本规划中实现。

## 7. 假设与依赖
- **假设**：企业已具备基础 IT 环境，可按版本要求部署 JDK 21、Maven、MariaDB、Redis、Nacos（或使用 Docker 容器化部署）。
- **假设**：短信/邮件服务可通过配置接入第三方服务商；开发环境可使用模拟验证码服务（VERIFICATION_CODE_MOCK=true）替代真实发送。
- **假设**：系统管理员角色（SUPER_ADMIN）与默认租户 DEFAULT 在系统初始化时由初始化脚本创建（管理员账号 admin / 密码 admin123），由企业方在首次登录后修改。
- **依赖**：网关认证依赖 auth-service 签发的 RS256 双 Token 与 Redis 中的登录态/黑名单/状态缓存，认证服务不可用将导致全部需要认证的请求失败（白名单接口除外）。
- **依赖**：OAuth 第三方登录依赖外部 OAuth 提供商（微信、Gitee 等 4 种）的授权服务可用性与回调配置正确。
- **依赖**：多租户数据隔离依赖 t_auth_tenant 租户表与各业务表的租户字段正确维护。
- **依赖**：密码找回、手机号变更、验证码注册等场景依赖验证码服务（短信/邮箱）的可用性。
